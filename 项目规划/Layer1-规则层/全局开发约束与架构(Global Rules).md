
# 全局开发约束与架构(Global Rules)

## 1. 核心工作流：API 先行与垂直切片
- **严禁大包大揽**：永远遵循“垂直切片”开发模式。一次只专注于一个细小的功能点（User Story）。
- **API 契约先行**：在编写任何前后端业务逻辑代码之前，必须先定义 API 契约（数据模型、路由、Request/Response JSON 结构、错误码）。
- **先搭骨架**：在实现具体逻辑前，必须先写出函数签名和带有详细注释的控制流伪代码，待我确认后再填充细节。



## 2. 控制流与状态管理

- **拒绝深层嵌套**：严禁使用超过两层的 `if/else` 嵌套。优先使用“提前返回（Early Return）”模式。
- **状态机思维**：当业务涉及 3 个及以上的状态流转时（如订单状态、审核状态），强制使用“状态机”模式（如 Enum 和状态流转字典/Map）来代替条件判断。必须显式定义非法状态跳转的报错。



## 3. 防御性编程与“悲观路径”

- **永远不要相信输入**：所有外部输入、API 参数、数据库查询结果在使用前必须进行校验（如使用 Zod, Joi 或原生类型检查）。
- **强制处理异常分支**：不要只写“Happy Path”。所有的网络请求、数据库操作、文件读写必须被 `try/catch` 包裹。
- **详细的错误日志**：在 `catch` 块中，不仅要抛出友好的上层错误（如 500 状态码），还要打印包含上下文变量的详细底层日志。



## 4. 代码交付标准

- **即时集成**：前端组件不需要 Mock 数据，必须直接调用已写好的真实后端 API 进行联调。
- **状态闭环**：前端涉及异步请求时，必须完整包含 3 个状态的处理逻辑：Loading（加载中）、Success（成功并刷新 UI）、Error（失败并给予用户 Toast 提示）。



## 5. 自动化测试与验证 (Testing & Verification)

- **契约驱动验证**：在完成后端 API 切片后，必须为其编写自动化测试。测试用例必须严格对照第一步设计的“API 契约”，确保真实的 Request/Response 与契约完全一致。
- **强制测试“悲观路径” (Sad Paths)**：严禁只编写 Happy Path 测试。必须针对控制流中的每一个异常分支（例如：非法参数、外部依赖超时、签名验证失败）编写独立的测试用例，断言其是否抛出了正确的错误码。
- **状态机边界测试**：如果核心逻辑包含状态机，必须编写专门的测试用例来验证“非法状态跳转”（例如尝试将 `REFUNDED` 状态改为 `PENDING`），并断言其被正确拦截。
- **Mock 外部依赖**：在单元测试中，必须 Mock 掉所有真实的数据库查询和第三方 API 调用，只专注于验证当前函数的内部控制流走向。
