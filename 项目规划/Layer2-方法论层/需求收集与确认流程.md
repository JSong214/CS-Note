# 需求收集与确认流程

> **文档定位**：Layer 2 — 方法论层（用于项目启动和客户沟通）
> **核心原则**：在写第一行代码之前，确保你和客户对"做什么"达成**书面一致**。
> **耗时参考**：小项目 1-3 天，中型项目 1 周

---

## 一、需求阶段流程总览

```
客户初次接触
     │
     ▼
┌─────────────┐
│ Step 1      │  首次访谈（业务 + 技术 + 项目管理三维问题框架）
│ 客户访谈    │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ Step 2      │  整理访谈内容，输出 PRD 草稿
│ 起草 PRD    │  明确 MVP 范围，排除二期功能
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ Step 3      │  技术可行性评估，识别高风险项
│ 技术评估    │  评估工期，制定里程碑计划
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ Step 4      │  发给客户确认，至少获得书面/邮件确认
│ 需求确认    │  签字 or 邮件回复：「确认以上需求」
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ Step 5      │  需求范围冻结，后续变更走变更单流程
│ 冻结范围    │
└─────────────┘
```

## 二、首次客户访谈清单

### 2.1 业务层问题（必问）

```markdown
□ 这个产品/功能要解决什么核心问题？
  → 追问：如果不做这个功能，目前是怎么解决的？

□ 目标用户是谁？他们的典型使用场景是什么？
  → 追问：用户的技术能力如何？需要考虑学习成本吗？

□ 你认为最核心的 3 个功能是什么？
  → 目的：逼迫客户做优先级排序，避免"全都重要"

□ 你有可以参考的竞品或原型图吗？
  → 有原型图可以减少 50% 的需求歧义

□ 成功的标准是什么？上线后怎么判断这个产品做成功了？
```

### 2.2 技术层问题（需了解）

```markdown
□ 预期的用户规模？
  → 100 人 or 10 万人 → 决定架构复杂度和成本

□ 是否有已有系统需要对接？
  → 老旧系统集成是最大的风险点，需要额外评估

□ 对响应速度、在线时长有什么要求？
  → 定义 SLA（如：核心接口 P99 < 500ms，可用性 ≥ 99.9%）

□ 数据是否涉及隐私/合规要求？
  → GDPR、网络安全法、等保 2.0、用户数据安全级别

□ 是否需要多语言、多时区支持？

□ 移动端适配需求？（响应式 or 独立 App）
```

### 2.3 项目管理层问题（边界保护）

```markdown
□ 期望的上线时间是什么？是否有硬性 Deadline？
  → 了解是否有节假日、促销节点等外部约束

□ 预算范围是什么？
  → 帮助判断功能范围是否合理

□ 谁是最终决策人？
  → 避免多人拍板导致需求反复（"我老板说要改"）

□ 验收标准是什么？「做完」的定义是什么？
  → 明确量化：所有 MVP 功能可用 + 无 P0 Bug + 部署上线

□ 如果我提出需求变更，你们的决策流程是什么？多久能给回复？
```

### 2.4 访谈注意事项

```markdown
⚠️ 警惕信号（遇到时需额外谨慎）：
- 客户说"就是个简单的小东西，很快能做完"→ 往往不简单
- 客户说"需求还没完全想好，边做边看"→ 需求蔓延风险极高
- 客户说"参考竞品 X 做个一样的"→ 竞品功能远比看起来复杂
- 决策人不在场，中间人传达需求→ 信息失真风险高

✅ 好的访谈习惯：
- 全程录音或记录文字（获得客户同意后）
- 访谈结束后 24 小时内发送会议纪要邮件
- 用客户的语言描述需求，不用技术术语
- 对不确定的需求，明确写上"待确认"而不是自行假设
```

## 三、需求文档（PRD）编写规范

### 3.1 何时写 PRD

```
独立开发者的 PRD 不需要 50 页，但必须：
✅ 够清晰：任何人读完都能理解要做什么
✅ 够防误解：歧义点提前消除，不留"理解空间"
✅ 经过确认：客户签字或书面确认
✅ 有变更记录：任何修改都有迹可查
```

### 3.2 PRD 必须包含的要素

| 要素 | 目的 | 是否必须 |
|---|---|---|
| 项目概述 | 一句话定义项目 | ✅ 必须 |
| 用户角色（Personas） | 明确服务对象 | ✅ 必须 |
| 功能列表（用户故事） | 明确做什么，不做什么 | ✅ 必须 |
| 非功能性需求 | 性能、安全、兼容性 | ✅ 必须 |
| 验收标准 | 定义"完成"的边界 | ✅ 必须 |
| UI/UX 参考 | 减少视觉歧义 | 建议有 |
| 数据流图 | 复杂业务必须有 | 视情况 |
| 变更记录 | 追溯历史修改 | ✅ 必须 |

## 四、技术可行性评估

### 4.1 评估维度与风险等级

在签合同/收款前，必须评估以下风险项：

| 风险项 | 评估结论 | 评估说明 | 应对措施 |
|---|---|---|---|
| 第三方 API 依赖（微信支付、短信、地图等） | 可行 / 存疑 / 高风险 | | |
| 数据量级（是否需要分库分表/缓存架构） | 可行 / 存疑 / 高风险 | | |
| 实时性需求（WebSocket、消息推送） | 可行 / 存疑 / 高风险 | | |
| 老系统数据迁移（数据格式、数据清洗） | 可行 / 存疑 / 高风险 | | |
| 合规/安全要求（等保、GDPR） | 可行 / 存疑 / 高风险 | | |
| 特殊算法/AI 集成 | 可行 / 存疑 / 高风险 | | |
| 跨平台支持（App + Web + 小程序） | 可行 / 存疑 / 高风险 | | |

### 4.2 风险等级定义

```
🟢 可行：有成熟方案，开发经验充足，风险可控
🟡 存疑：有方案但有不确定性，需要 PoC（概念验证）后决定
🔴 高风险：超出当前技术能力，或工期估算极不准确，建议明确告知客户
```

### 4.3 工期估算原则

```
独立开发者工期估算口诀：
1. 先拆分：将所有功能分解到"垂直切片"粒度（每个切片约 0.5-2 天）
2. 后加总：所有切片工期相加得到"净开发时间"
3. 再乘系数：
   - 简单项目（需求清晰、技术熟悉）：× 1.5
   - 中等项目（部分技术有学习成本）：× 2.0
   - 复杂项目（集成多个系统、需求模糊）：× 2.5-3.0
4. 最后加缓冲：测试 + 修复 + 部署 + 交接 ≈ 总开发时间的 30%
```

## 五、需求确认与变更管理

### 5.1 需求确认方式

```markdown
优先级从高到低：
1. ✅ 最佳：双方签字的纸质/PDF 文档
2. ✅ 推荐：客户邮件明确回复"确认以上需求，同意进入开发"
3. ⚠️ 可接受：即时通讯（微信/钉钉）截图，需截图存档
4. ❌ 禁止：口头确认（无任何记录）
```

**确认邮件模板：**

```
主题：[项目名称] 需求文档 v1.0 确认请求

您好，

请查阅附件中的《[项目名称] 需求文档 v1.0》，
本文档包含：
- 项目概述与目标
- MVP 功能范围（共 X 项用户故事）
- 二期不做的功能明细
- 验收标准

如无异议，请回复本邮件"确认以上内容，同意进入开发阶段"即可。

后续任何功能范围调整，需通过变更单流程处理，
并可能影响工期和费用，请知悉。

感谢配合！
```

### 5.2 需求变更管理（变更单流程）

**重要原则**：需求文档经双方确认后，功能范围进入**冻结期**。后续任何新增功能需求需提交变更申请，并重新评估工期和费用。

**变更单模板：**

```markdown
# 需求变更单 #001

**提出日期**：YYYY-MM-DD
**提出方**：客户 / 开发者
**优先级**：P0（必须做）/ P1（重要）/ P2（可以做）

## 变更描述
原需求：...
变更为：...
变更原因：...

## 影响评估
- 工期影响：+X 个工作日
- 费用影响：增加 ¥X
- 技术风险：无 / 需重新评估
- 受影响的已有功能：...

## 决策
- [ ] 接受变更（工期/费用调整已确认）
- [ ] 推迟到 v2 版本
- [ ] 拒绝变更

**客户确认**：________________________  日期：__________
**开发者确认**：______________________  日期：__________
```

## 六、流程检查清单

### 6.1 进入开发前的必查项

```markdown
## 需求阶段完成检查 ✅

基本信息
- [ ] 客户访谈完成，所有疑问已澄清
- [ ] PRD 文档 v1.0 已输出

文档内容
- [ ] 项目概述清晰（一句话能说明白）
- [ ] 用户角色已定义（至少包含所有主要角色）
- [ ] MVP 功能已用用户故事格式描述
- [ ] 二期功能已明确列出并排除在外
- [ ] 非功能性需求已定义（性能、安全、兼容性）
- [ ] 验收标准可量化、可验证

确认与签字
- [ ] 客户已书面（邮件/签字）确认 PRD
- [ ] 变更冻结期声明已告知客户

技术评估
- [ ] 技术可行性评估表已填写
- [ ] 高风险项已识别并告知客户
- [ ] 工期估算已完成（使用乘系数方法）
- [ ] 里程碑计划已制定

合同保障（推荐）
- [ ] 合同中包含付款里程碑（不要尾款全付）
- [ ] 变更单流程已在合同中约定
```
