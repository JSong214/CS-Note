## Phase 0：需求阶段（客户对接）

> **目标**：在写第一行代码之前，确保你和客户对"做什么"达成书面一致。
> **耗时参考**：小项目 1-3 天，中型项目 1 周

### 0.1 首次客户访谈清单

进行第一次客户会谈前，准备以下问题框架：

**业务层问题（必问）**
- 这个产品/功能要解决什么核心问题？
- 目标用户是谁？他们的使用场景是什么？
- 你认为最核心的 3 个功能是什么？（逼迫客户做优先级排序）
- 你有可以参考的竞品或原型图吗？

**技术层问题（需了解）**
- 预期的用户规模？（100 人还是 100 万人，决定架构复杂度）
- 是否有已有系统需要对接？（老旧系统集成是最大的风险点）
- 对响应速度、在线时长有什么要求？（定义 SLA）
- 数据是否涉及隐私/合规要求？（GDPR、等保、用户数据安全）

**项目管理层问题（边界保护）**
- 期望的上线时间是什么？
- 预算范围是什么？
- 谁是最终决策人？（避免多人拍板导致需求反复）
- 验收标准是什么？（"做完"的定义是什么）

### 0.2 需求文档（PRD）最小模板

> 不需要写 50 页的 PRD，独立开发者的 PRD 只需要够清晰、够防误解。

```markdown

## 项目概述
- 项目名称：
- 客户/委托方：
- 文档版本：v1.0 | 日期：YYYY-MM-DD
- 确认人签字：（双方确认后不可随意变更）

## 核心目标
一句话描述：本项目旨在帮助 [目标用户] 解决 [核心问题]。

## 用户角色（Personas）
| 角色 | 描述 | 核心诉求 |
|---|---|---|
| 普通用户 | ... | ... |
| 管理员 | ... | ... |

## 功能列表（用户故事格式）
### MVP 范围（必须有）
- [ ] 作为 [用户]，我希望 [做某事]，以便 [获得某种价值]
- [ ] ...

### 二期功能（本期不做，明确排除在外）
- 功能 X：留待 v2
- 功能 Y：留待 v2

## 非功能性需求
- 性能：核心页面首屏加载 < 3s
- 安全：用户密码必须加密存储，接口必须鉴权
- 兼容性：支持 Chrome / Safari 最近两个大版本

## 验收标准
- [ ] 所有 MVP 功能正常可用
- [ ] 无 P0/P1 级 Bug
- [ ] 部署至生产环境且客户可访问

## 变更记录
| 日期 | 变更内容 | 提出方 | 是否影响工期 |
|---|---|---|---|
```

**⚠️ 重要原则**：需求文档必须由**客户签字或书面（邮件）确认**。后续任何需求变更，走"变更单"流程，而不是口头答应再默默加班。

### 2.1 Git 工作流规范（现有文档缺失）

独立开发也需要严格的 Git 规范，原因：代码回滚、功能隔离、清晰的变更历史。

**推荐分支策略（简化版 GitFlow）：**

```
main          ← 永远指向生产可部署的代码
  └── develop ← 日常集成分支
        └── feature/user-register   ← 每个垂直切片一个分支
        └── feature/post-like
        └── fix/login-bug
        └── hotfix/security-patch   ← 直接从 main 分出，修完合回 main+develop
```

**Commit 消息规范（Conventional Commits）：**

```
# 格式：<type>(<scope>): <subject>

feat(auth): 完成用户注册接口及前端表单
fix(order): 修复订单状态流转越权问题
test(user): 补充注册接口悲观路径测试用例
docs(api): 更新 Swagger 文档至 v1.2
refactor(handler): 提取统一错误处理中间件
chore(ci): 配置 GitHub Actions 自动化测试
```

**强制 pre-commit 检查（结合 husky）：**

```bash
# .husky/pre-commit
npm run lint       # 前端 ESLint 检查
go vet ./...       # Go 静态分析
go test ./...      # 跑全量单元测试（快速）
```

### 2.2 环境隔离规范

```
开发环境（local）    → 开发者本机，可随意破坏
预发布环境（staging） → 模拟生产，用于客户验收
生产环境（production）→ 真实用户使用，最小权限原则
```

**环境变量管理（敏感信息绝不进代码库）：**

```bash
# .env.development（可以提交）
API_BASE_URL=http://localhost:8080
DB_HOST=localhost

# .env.production（绝不提交，通过 CI/CD 平台注入）
DB_PASSWORD=******
JWT_SECRET=******
REDIS_URL=******
```

```
# .gitignore 必须包含
.env.production
.env.staging
*.secret
```

### 3.1 安全规范（现有文档缺失，风险极高）

**身份认证（JWT 标准实践）：**

```go
// ✅ 正确：Access Token 短有效期 + Refresh Token 轮换
AccessToken  有效期：15 分钟
RefreshToken 有效期：7 天，用后即废（单次使用）

// ❌ 错误：Token 永不过期 或 有效期 30 天
```

**前端 Token 存储（现有文档未提及，高频安全漏洞）：**

```typescript
// ❌ 危险：存在 localStorage（XSS 攻击可以直接读走）
localStorage.setItem('token', accessToken)

// ✅ 推荐方案 A：内存存储（页面刷新会丢失，需配合 Refresh Token 自动续期）
let accessToken: string | null = null

// ✅ 推荐方案 B：HttpOnly Cookie（后端 Set-Cookie，JS 无法读取，防 XSS）
// 后端设置 Cookie 时加上 HttpOnly; Secure; SameSite=Strict
```

**API 安全清单（每个接口上线前必查）：**

```markdown
- [ ] 是否正确设置了 CORS 白名单（不能是 *）
- [ ] 所有需要登录的接口是否挂载了 Auth 中间件
- [ ] 分页接口是否有 pageSize 上限（防止 limit=99999）
- [ ] 文件上传是否校验了文件类型和大小
- [ ] 批量操作接口是否有权限校验（防止 A 删除 B 的数据）
- [ ] SQL 查询是否全部使用了参数化查询（ORM 一般已保障）
- [ ] 敏感字段（密码、手机号）是否在 Response 中被过滤掉
- [ ] 是否对高频接口（如登录、注册）做了限流（Rate Limiting）
```

**Go 限流中间件示例：**

```go
// 使用 golang.org/x/time/rate 或 github.com/ulule/limiter
// 登录接口：同一 IP，1分钟内最多 5 次尝试
```

### 3.2 数据库设计规范（现有文档未覆盖）

**通用字段约定（所有表必须包含）：**

```sql
-- 每张表的标准字段
id         BIGSERIAL PRIMARY KEY,
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
```

### 5.1 Docker 化标准配置

**后端 Dockerfile（Go 多阶段构建）：**

```dockerfile
# 构建阶段
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server ./cmd/server

# 运行阶段（最小化镜像）
FROM alpine:3.19
RUN apk add --no-cache ca-certificates tzdata
WORKDIR /app
COPY --from=builder /app/server .
COPY configs/ ./configs/
EXPOSE 8080
CMD ["./server"]
```

### 5.2 GitHub Actions CI/CD 流水线

```yaml
# .github/workflows/ci.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test-backend:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.22'
      - run: go test ./... -race -coverprofile=coverage.out
      - run: go vet ./...

  test-frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run type-check
      - run: npm run test:unit

  deploy-staging:
    needs: [test-backend, test-frontend]
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Staging
        # 使用 SSH 或云平台 CLI 部署到预发布环境
        run: echo "部署到预发布环境"

  deploy-production:
    needs: [test-backend, test-frontend]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production  # 需要人工审批
    steps:
      - name: Deploy to Production
        run: echo "部署到生产环境"
```

### 5.3 Nginx 配置（前后端同域解决 CORS）

```nginx
# /etc/nginx/conf.d/myapp.conf
server {
    listen 80;
    server_name yourdomain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name yourdomain.com;

    ssl_certificate /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;

    # 前端静态文件
    location / {
        root /var/www/frontend/dist;
        try_files $uri $uri/ /index.html;  # SPA 路由支持
    }

    # API 转发（同域，彻底解决 CORS 问题）
    location /api/ {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## Phase 6：监控与运维（现有文档缺失）

> 上线不是终点，可观测性决定了你能不能快速发现和解决问题。

### 6.1 日志规范

结合你的 Global Rules 中"详细的错误日志"要求，推荐使用结构化日志（JSON 格式）：

```go
// 推荐使用 zerolog 或 zap（Go 高性能结构化日志库）
log.Error().
    Err(err).
    Str("trace_id", traceID).
    Str("user_id", userID).
    Str("action", "register").
    Str("email", email).
    Msg("用户注册失败：数据库写入超时")

// 输出 JSON：
// {"level":"error","trace_id":"abc123","user_id":"","action":"register","email":"test@example.com","error":"dial tcp: timeout","message":"用户注册失败：数据库写入超时","time":"..."}
```

**日志等级使用规范：**

| 等级 | 使用场景 |
|---|---|
| DEBUG | 仅开发环境，详细调试信息 |
| INFO | 重要业务事件（用户登录、订单创建成功） |
| WARN | 异常但可恢复（缓存未命中、重试成功） |
| ERROR | 请求失败，需要关注（数据库错误、第三方 API 超时） |
| FATAL | 服务无法启动，立即触发报警 |

### 6.2 错误追踪

推荐集成 **Sentry**（开源可自部署，或使用 SaaS 版）：

```go
// Go 后端集成 Sentry
import "github.com/getsentry/sentry-go"

func init() {
    sentry.Init(sentry.ClientOptions{
        Dsn: os.Getenv("SENTRY_DSN"),
        Environment: os.Getenv("APP_ENV"),
        // 仅在生产环境开启
        TracesSampleRate: 0.1,
    })
}

// 在 catch 块中上报错误
sentry.CaptureException(err)
```

### 6.3 关键指标监控

最小化监控配置（独立开发者可接受的成本）：

```markdown
## 必须监控的指标

1. 服务可用性：/api/v1/health 接口每分钟探测一次
   - 工具：UptimeRobot（免费版足够）、Ping.gg

2. 错误率：5xx 错误占比 > 1% 触发告警
   - 工具：Sentry 内置告警

3. 数据库连接：连接池耗尽告警
   - 方式：Prometheus + Grafana（轻量版）

4. 磁盘空间：服务器磁盘使用率 > 80% 告警
   - 工具：云服务器控制台内置告警
```

### 3.2 流程层面的三大核心建议

**建议一：建立"需求冻结"机制**

独立开发者最大的风险不是技术难度，而是**需求蔓延（Scope Creep）**。每次"小小的修改"都会侵蚀你的利润和时间。建议在需求文档中明确写入：

> "本文档经双方确认后，功能范围进入冻结期。后续任何新增功能需求需提交变更申请，并重新评估工期和费用。"

**建议二：引入"可演示里程碑"节奏**

每完成 2-3 个垂直切片，主动给客户演示一次（视频录屏 + 说明即可）。好处是：
- 及早发现方向偏差，避免最后全部推翻
- 建立客户信任，降低尾款风险
- 倒逼自己保持"随时可演示"的代码质量

**建议三：用 Makefile 统一所有命令**

无论是开发还是交接，所有操作都通过 `make` 命令执行，消除"在我机器上能跑"问题：

```makefile
.PHONY: dev build test lint migrate deploy

dev:       ## 启动开发环境
	docker-compose up -d db redis
	air -c .air.toml  # Go 热重载

build:     ## 构建生产镜像
	docker build -t myapp:$(VERSION) .

test:      ## 运行所有测试
	go test ./... -race -cover

lint:      ## 代码检查
	golangci-lint run ./...
	cd frontend && npm run lint

migrate:   ## 执行数据库迁移
	migrate -path ./migrations -database $(DB_URL) up

migrate-down: ## 回滚最近一次迁移
	migrate -path ./migrations -database $(DB_URL) down 1
```
